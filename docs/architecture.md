# Architecture

## The idea in one paragraph

A conventional monitoring system watches sensor values against fixed limits. It
tells you a machine has failed, usually at the moment the failure becomes
expensive. A digital twin watches sensor values against *what a model of that
machine says those values should be*, which lets you see a machine stop
behaving like itself long before any limit is crossed. Everything in this
repository follows from that one difference.

## Two passes per tick

`twin-core` solves the entire plant twice on every tick.

```
                 ┌──────────────────────────────────────────────┐
   setpoints ───▶│  REAL pass                                   │
   ambient       │  physics(design, accumulated wear, faults)   │──▶ + sensor noise ──▶ observed
                 └──────────────────────────────────────────────┘
                                                                        │
                 ┌──────────────────────────────────────────────┐       │
 measured  ─────▶│  REFERENCE pass                              │       ▼
 conditions      │  physics(design, wear = 0)                   │──▶ expected ──▶ residual = observed − expected
                 └──────────────────────────────────────────────┘                          │
                                                                                           ▼
                                                     robust z-score → alert · health · RUL · OEE
```

The real pass carries whatever wear has accumulated plus any injected fault,
and its output gets measurement noise added — that is what a historian would
have recorded. The reference pass runs the same asset as-new and noise-free.

The difference between them is the **residual**, and it is the only thing the
analytics layer reasons about. This is why nothing in the codebase fakes a
symptom: a worn impeller produces falling flow because
`H = H₀ − aQ²` says it must, not because a branch writes a smaller number.

## Why the reference is an observer, not a parallel plant

The reference pass is fed **the conditions each real asset actually measured**,
not conditions generated by a second simulated plant. This matters more than it
sounds, and the repository has the scar tissue to prove it.

The first implementation ran the reference as a free-standing parallel plant.
Inject a worn impeller into the feed pump and the real exchanger was starved
while the reference exchanger still saw design flow — so every asset
*downstream* of the fault showed a huge residual. The console raised critical
alerts on the reactor and the chiller and none at all on the pump. The single
loudest alert was the reactor's jacket valve: a controller output whose entire
job is to absorb upstream disturbance, and therefore the most sensitive
possible detector of something happening somewhere else.

Feeding each reference asset the measured inputs its real counterpart saw
(`ObserverBus` in `simulation/physics.py`) makes the surviving residual local to
that asset. Reactor, gearbox and chiller faults now alert only on themselves,
and a pump fault leads the feed with pump alerts.

The two passes are also **interleaved asset by asset** rather than run as two
sweeps. Some signals are read a tick late by design — the chiller is solved
before the reactor whose jacket duty it serves — so a reference sweep run after
the real sweep would read this tick's value where its counterpart read last
tick's. That one-tick mismatch produced a residual on every transient.

## Services

```
apps/console  ──── WebSocket /api/v1/stream ────▶  services/twin-core
  React + TS         REST /api/v1/*                  FastAPI
  three.js                                           simulation engine
  recharts                                           analytics
                                                     in-memory history
```

`twin-core` holds all state in process. That is a deliberate choice, not an
omission: ten assets at 1 Hz produce ~73 series, and an hour of history is a
few megabytes of floats. Keeping it in memory makes chart requests
sub-millisecond with no database to operate. `store/timeseries.py` is the only
module that knows where points live — swapping it for TimescaleDB or InfluxDB
is a matter of reimplementing one class.

| `app/plant/aurora_works.yaml` | As-designed registry: identity, topology, placement, nameplate data |
| `app/domain/models.py` | The typed surface shared by the engine and the API |
| `app/simulation/physics.py` | First-principles asset models, the process bus, the observer bus |
| `app/simulation/degradation.py` | Wear mechanisms — the hidden state the analytics must infer |
| `app/simulation/faults.py` | Injectable failure mechanisms; act on rates, never on readings |
| `app/simulation/engine.py` | The tick loop, asset state machine, work-order generation |
| `app/simulation/scenarios.py` | What-if projection over a forked twin |
| `app/analytics/anomaly.py` | Residual detection: median/MAD, EWMA, persistence |
| `app/analytics/rul.py` | Theil–Sen remaining-useful-life projection |
| `app/analytics/kpis.py` | OEE, energy intensity, cost, carbon |
| `app/store/timeseries.py` | Bounded in-memory rings |
| `app/api/*` | HTTP and WebSocket surface |

## Boot sequence

Starting the process is not free, and it should not be. `TwinEngine.prime()`
runs two phases before the service accepts a request:

1. **Settle** — 300 physics-only ticks. The reactor needs several residence
   times to reach equilibrium. A detector that characterised "normal" during
   that transient would freeze a baseline taken from a plant that was still
   moving, then alarm on the settled steady state.
2. **Warm** — 150 real ticks, so the residual detectors fit their baselines and
   the history buffers fill.

Total cost is about 450 ms, after which the twin answers its first request with
real history, a live detector and a populated work-order queue. Without phase 2
the service spends its first two minutes serving empty charts and a detector
that structurally cannot alert — which is indistinguishable, to anyone
watching, from a plant with no problems.

## Simulated time

The twin runs at a configurable speed-up (`TWIN_SIM_SPEED`, default 60×), so
one wall-clock second advances a simulated minute. Degradation that would take
months is visible in a demo, and the *shape* of every trend is preserved
because every rate in the system is expressed per simulated day.

## Known limitations

Stated plainly, because a twin that oversells itself is worse than none:

- **Residuals are not perfectly stationary.** Some are proportional to load, so
  a large change in operating point can move a z-score without any change in
  asset health. Secondary alerts on neighbouring equipment during a big upset
  are real, not spurious, but they are symptoms rather than causes. Ranking
  (severity, then deviation) puts the true cause at the top of the feed;
  explicit causal grouping is not implemented.
- **The compressor is an empirical model**, not a polytropic one. On an
  oil-flooded screw the injected oil absorbs most of the heat of compression,
  so a textbook adiabatic discharge temperature would be badly wrong.
- **Faults are single-mechanism.** Real failures interact; these do not, beyond
  lubricant degradation accelerating the mechanical modes on the gearbox.
- **No persistence.** Restarting the process restarts the plant's history.
